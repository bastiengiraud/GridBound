# What certflow can verify: the four modes

| Mode | Question | Call | Page |
|---|---|---|---|
| **Dispatch NN** (the paper) | Does a network trained on OPF data (loads → Pg, Vg) keep every operational limit for every load in a set? If not, which certified correction fixes it? | `verify_dispatch` | [dispatch.md](dispatch.md) |
| **RL 1: next-step safety** | For every load in a box: which actions can the agent take, and is each one safe one step later? | `RLAuditor.next_step` | [rl_next_step.md](rl_next_step.md) |
| **RL 2: measurement noise** | How much sensor noise can the agent take before it changes its action, or before it can pick an unsafe action? | `RLAuditor.noise_robustness` | [rl_noise.md](rl_noise.md) |
| **RL 3: multi-step reachability** | Which states can the agent drive the grid into over several steps, while the loads keep changing? | `RLAuditor.multi_step` | [rl_multistep.md](rl_multistep.md) |

Each page covers four things:

- **API:** the call and its options.
- **How it works:** the method, step by step.
- **Output:** the rendered report and figure from a small reproducible example.
- **Limits:** what the result does and does not guarantee.

Every figure and report here is regenerated by one command (about 5 minutes):

```bash
python docs/make_figures.py
```

The examples use two small grids:

- **MATPOWER case9:** the dispatch NN.
- **A 6-bus MV feeder:** 110/20 kV transformer with an on-load tap changer, four MV buses with loads and two PV
  parks ([`examples/feeder_demo.py`](../../examples/feeder_demo.py)). Its demo agent is trained in a few seconds to
  imitate a voltage rule:
  - tap +1 when voltages are high;
  - tap −1 when they are low;
  - the PV park absorbs 1 MVAr in between;
  - idle otherwise.

## The common core

All four modes share one pipeline and differ in where the uncertainty enters and in what is checked.

1. **Input set:** an affine set of loads, x = c + G·e with e ∈ [−1, 1]ᴷ. Its symbols e are the directions the
   verifier splits along.
2. **Certified power flow:** a Krawczyk proof that the AC power flow has a unique solution for every e. The grid
   state comes out as degree-2 Taylor models in e (`certflow.krawczyk`, `certflow.power.pfcert.enclose_pf`).
3. **Observables:** voltages, loadings, flows and injections are formed from those Taylor models, keeping the
   correlation with e (`certflow.power.quantities`).
4. **Network:** pushed through the NN with DeepZ, including the deployed float32 rounding (`certflow.nn`). For an
   agent, the masked argmax then gives the set of actions it can take.
5. **Splitting:** the input set is split adaptively where a proof fails or a decision is ambiguous
   (`certflow.split`, `certflow.policy`).

Verdicts:

| Verdict | Meaning |
|---|---|
| **SAFE** | proven for every input in the set, floating-point rounding included |
| **UNSAFE** | a concrete counterexample was found, re-simulated with a plain power flow, and printed |
| **NOT PROVEN** | the proof failed somewhere and no counterexample was found |

Every report also carries a Monte-Carlo cross-check of the certified claims.
